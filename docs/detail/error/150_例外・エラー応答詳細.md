# 150_例外・エラー応答詳細

本書は **GlobalExceptionHandler（`@RestControllerAdvice`）の実装**を唯一の根拠として、例外ハンドリングとエラー応答の仕様を定義します。
エラーレスポンスのキー構成・HTTP ステータス・エラーコードは**実装と整合**しています。

---

## 1. エラーレスポンス フォーマット（固定）

GlobalExceptionHandler の `ErrorBody` は次の**固定スキーマ**です。

```json
{
  "timestamp": "2025-10-22T00:00:00Z",
  "traceId": "a1b2c3d4e5f6",
  "errorCode": "VAL-0000",
  "message": "入力値が不正です。",
  "field": "member.name",
  "details": ["BindException"]
}
```

### 1.1 フィールド定義

| フィールド       | 型              | 必須 | 説明                                       |
| ----------- | -------------- | -- | ---------------------------------------- |
| `timestamp` | string         | ○  | ISO-8601（UTC）。サーバ側で生成。                   |
| `traceId`   | string         | ○  | リクエスト相関用 ID。フィルタ／MDC から取得。空文字の可能性あり。     |
| `errorCode` | string         | ○  | エラーの分類コード（下表「コード体系」参照）。                  |
| `message`   | string         | ○  | 利用者向けの簡潔なメッセージ（日本語）。内部情報を含めない。           |
| `field`     | string or null | 任意 | フィールド起因エラー時に設定（例：`"code"`）。無関係なら `null`。 |
| `details`   | array<string>  | 任意 | 技術的な補助情報（例外クラス名など）。PII・秘匿情報は**含めない**。    |

> 注：**内部例外メッセージ、スタックトレース、SQL 文**などの内部情報は応答に含めません（ログ側で管理）。

---

## 2. HTTP ステータスと例外のマッピング

GlobalExceptionHandler の各 `@ExceptionHandler` に対応する**確定マッピング**です。

|   ステータス | 例外クラス                             | errorCode  | message（既定）                                      | field              | details                               |
| ------: | --------------------------------- | ---------- | ------------------------------------------------ | ------------------ | ------------------------------------- |
| **400** | `MethodArgumentNotValidException` | `VAL-0000` | 先頭の `FieldError#defaultMessage` もしくは「不正な入力です。」   | 該当フィールド名 or `null` | 空配列                                   |
| **400** | `BindException`                   | `VAL-0000` | 同上                                               | 同上                 | 空配列                                   |
| **400** | `ConstraintViolationException`    | `VAL-0000` | 先頭の `ConstraintViolation#message` もしくは「不正な入力です。」 | `null`             | 空配列                                   |
| **400** | `HttpMessageNotReadableException` | `VAL-0001` | 「リクエストボディの形式が不正です。」                              | `null`             | `["HttpMessageNotReadableException"]` |
| **400** | `IllegalArgumentException`        | `VAL-0002` | 例外メッセージ or 「不正なリクエストです。」                         | `null`             | `["IllegalArgumentException"]`        |
| **409** | `DataIntegrityViolationException` | `VAL-0105` | 「一意制約違反です。」                                      | `"code"`（暫定）       | `["DataIntegrityViolationException"]` |
| **500** | `Exception`（その他すべて）               | `SYS-0001` | 「サーバ内部エラーが発生しました。」                               | `null`             | `["Exception"]`                       |

> 補足：409 の `field` は現状 `"code"` を固定返却しています（実装準拠）。エンティティ別のユニークキーに対応する場合は将来拡張で差し替えます。

## 3. エラーコード体系（実装準拠・当面版）

現在の実装が返却しうる `errorCode` は以下のとおりです。

* **VAL-0000** … 入力値不正（Bean Validation / バインド / パラメータ制約）
* **VAL-0001** … JSON 形式不正（パース不能）
* **VAL-0002** … 不正引数（業務前段の簡易検証で弾くケース）
* **VAL-0105** … 一意制約違反（ユニークインデックス衝突）
* **SYS-0001** … サーバ内部エラー（予期しない例外のフォールバック）

> 将来的に、フィールド別・ルール別に細分化した **FFRR 型（例：`VAL-0101` 必須、`VAL-0102` 長さ、`VAL-0105` 一意）**へ移行予定です。現時点では **`VAL-0000` を共通仮コード**として運用します（GlobalExceptionHandler 実装コメントの方針に一致）。

## 5. 運用ルール

1. **ユーザー向け文言**

   * `message` は簡潔・日本語・非技術的。内部構造・SQL・スタックトレースは含めない。
2. **詳細情報（details）**

   * 原則として**例外クラス名など低リスクの技術情報のみ**。個人情報・秘密情報は**出力禁止**。
3. **traceId の相関**

   * すべての応答に `traceId` を付与し、ログ（MDC）と相関可能にする。空値になる場合はログ側で補完。
4. **将来拡張（FFRR 移行）**

   * `VAL-0000` を API/ドメイン層で **具体的コード（例：`VAL-0101` 必須、`VAL-0102` 長さ）**に差し替える拡張を計画。差し替え時は本書を更新する。
5. **一意制約の `field`**

   * 現状 `"code"` 固定。エンティティ別ユニークキー対応が必要になり次第、ハンドラの分岐と本書の表を更新する。
