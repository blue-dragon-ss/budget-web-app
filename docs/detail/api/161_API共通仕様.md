# 161_API共通仕様

## 1. API基盤
### 1.1 パスとリソース
- ベースパスは `ApiPaths.API_V1`（`/api/v1`）。会員系リソースは `ApiPaths.MEMBERS_BASE` で `/api/v1/members` にマッピングされ、作成操作は `ApiPaths.CREATE` の `/create` を付与する。したがって会員登録 API は `POST /api/v1/members/create` となる。

### 1.2 ID と日時
- レスポンス生成時の ULID（26 文字）は `UlidCreator` を利用して `MemberEntity.id` に設定する。
- `MemberEntity` は `@PrePersist` / `@PreUpdate` で `createdAt` と `updatedAt` を `Instant.now()` に揃える。
- 共通ユーティリティ `IdGenerator.newId()` はハイフン区切りのランダム UUID（36 文字）を返す。`CommonHeadersFilter` や `RequestIdFilter` がヘッダ値を採番する際の唯一の生成点となっており、将来的に ULID へ切り替える場合は本メソッドを差し替える構成になっている。

## 2. 共通ヘッダ運用
### 2.1 トレーシング
- `CommonHeadersFilter`（`@Order(1)` を付与した `OncePerRequestFilter`）が `X-Trace-Id` を受信し、未指定または空白の場合は `IdGenerator.newId()` が返す UUID を採番する。
- 決定した値はリクエスト属性（キー: `LogFields.TRACE_ID`）、レスポンスヘッダ、および MDC に保存し、レスポンス送信後に MDC から除去する。
- Controller／サービス層は `TraceIdHolder.get()` から MDC のトレース ID を参照し、`MemberResponse.traceId` に設定する。フィルタを通過していないケースでも空文字（`""`）を返して NullPointerException を防ぐ。

### 2.2 リクエスト ID
- `RequestIdFilter`（`OncePerRequestFilter`）が `X-Request-Id` を受信し、未指定または空白の場合は `IdGenerator.newId()` による UUID を割り当てる。
- 値はレスポンスヘッダへ返却され、MDC には `LogFields.RID` として処理中のみ保持される（レスポンスボディには出力しない）。
- フィルタ終了時に MDC から `rid` を必ず除去する。

### 2.3 冪等性キー
- `X-Idempotency-Key` は `CommonHeadersFilter` が空白のみを除外してリクエスト属性および MDC（`LogFields.IDEMPOTENCY_KEY`）にそのまま格納する（トリムや小文字化は行わない）。
- `MemberService` は `StringUtils.normalizeIdempotencyKey` で前後空白を除去し小文字化した値を使用する。空文字列は `null` として扱う。
- フィルタ完了時には MDC から `idempotencyKey` を必ず除去し、リクエスト間で値が漏れないようにする。

### 2.4 セキュリティ・キャッシュヘッダ
- すべてのレスポンスに以下が付与される：`Referrer-Policy: no-referrer`、`X-Frame-Options: DENY`、`X-Content-Type-Options: nosniff`、`Cache-Control: no-store`。
- HTTPS 通信 (`HttpServletRequest.isSecure() == true`) の場合は `Strict-Transport-Security: max-age=31536000; includeSubDomains` を追加する。

## 3. 会員登録リクエスト仕様
### 3.1 入力フィールド
| フィールド | 型 | 必須 | 制約・正規化 |
| --- | --- | --- | --- |
| `code` | string | 必須 | `@NotBlank`、長さ 1〜50。`StringUtils.trim` 済みの値を保存。|
| `name` | string | 必須 | `@NotBlank`、長さ 1〜200。`StringUtils.trim` 済みの値を保存。|
| `email` | string | 任意 | 最大 320 文字、正規表現 `Regexes.EMAIL` で形式チェック。指定時はトリム＋小文字化して保存。|
| `note` | string | 任意 | 最大 10,000 文字。|

### 3.2 ヘッダ
- `Content-Type: application/json`
- `X-Trace-Id`／`X-Request-Id`（任意）：未指定時はサーバが生成し、レスポンスヘッダに反映する。
- `X-Idempotency-Key`（任意）：Create 系での再送対策。正規化後のキーとリクエストハッシュで冪等性制御を行う。

## 4. 正常レスポンス
- ステータス：`201 Created`
- ボディ構造（`MemberResponse`）
  ```json
  {
    "id": "01H......",          // ULID(26)
    "code": "mbr001",
    "name": "山田太郎",
    "email": "example@example.com", // 未指定時は null
    "note": "...",                   // 未指定時は null
    "createdAt": "2024-01-01T00:00:00Z", // `DateTimeFormatter.ISO_INSTANT`
    "updatedAt": "2024-01-01T00:00:00Z",
    "traceId": "6f0c..."              // `X-Trace-Id` と同一
  }
  ```
- 成功レスポンスは `IdempotentRequest.responseBody` に JSON キャッシュとして保存され、同一キー再実行時に再利用される。
- `TraceIdHolder.get()` は MDC の `traceId` を参照し、未設定時は空文字を返すため、API 呼び出し外（バッチ等）での利用時にも安全に呼び出せる。

## 5. エラー共通仕様
### 5.1 フォーマット
`GlobalExceptionHandler` はすべてのエラーを次の構造で返却する：
```json
{
  "timestamp": "2024-01-01T00:00:00Z",
  "traceId": "6f0c...",
  "errorCode": "VAL-0101",
  "message": "会員コードは必須です。",
  "field": "code",
  "details": ["MethodArgumentNotValidException"]
}
```
- `timestamp`: `Instant.now()`
- `traceId`: フィルタが `HttpServletRequest` 属性に保持した値を優先し、無い場合は MDC の `traceId` をフォールバックで取得する。
- `field`: フィールド特定できない場合は `null`
- `details`: 発生した例外クラス名などの補足（該当しない場合は空リスト）
- `ValidationErrorCodeResolver` がフィールドごとのエラーコードを解決し、該当しない場合は共通コード `VAL-0000` を採用する。

### 5.2 HTTP ステータスとエラーコード
| HTTP ステータス | 主なトリガー | エラーコード例 |
| --- | --- | --- |
| 400 Bad Request | Bean Validation（`MethodArgumentNotValidException`／`BindException`／`ConstraintViolationException`）、JSON パース失敗（`HttpMessageNotReadableException`）、不正リクエスト（`IllegalArgumentException`）、ユニークキー重複（`DuplicateValueException`） | `VAL-0101`、`VAL-0201`、`VAL-0303`、`VAL-0105`、`VAL-0000`、`VAL-0001` など |
| 409 Conflict | `IdempotencyConflictException`（同一キー異なる内容・処理中） | `IDEMP-0001`（内容差異）、`IDEMP-0002`（処理中） |
| 500 Internal Server Error | `UnexpectedPersistenceException`、その他未捕捉例外（`Exception` ハンドラで統一応答） | `SYS-0001` |

### 5.3 フィールド別エラーコード
`MemberFieldErrorCodeMapper` は Bean Validation の制約コードを次のエラーコードに正規化する。
| フィールド | 違反種別 | エラーコード |
| --- | --- | --- |
| `code` | 必須違反 (`@NotBlank`) | `VAL-0101` |
| `code` | 長さ (`@Size`) | `VAL-0102` |
| `code` | 重複 (`DuplicateValueException`) | `VAL-0105` |
| `name` | 必須違反 | `VAL-0201` |
| `name` | 長さ | `VAL-0202` |
| `email` | 長さ | `VAL-0302` |
| `email` | 形式 | `VAL-0303` |
| `note` | 長さ | `VAL-0402` |

### 5.4 エラーコード解決ロジック
- `ValidationErrorCodeResolver` は Spring コンテナに登録された `FieldErrorCodeMapper` を順番に評価し、`supports` した最初のマッパーが返すコードを採用する。該当しない場合は共通デフォルトコード `VAL-0000` を返す。
- `DuplicateValueException`／`IdempotencyConflictException`／`UnexpectedPersistenceException` はフィールド名とエラーコードを保持し、例外ハンドラがそのままレスポンスに反映する。

### 5.5 代表的なエラーメッセージ
- `ErrorMessage.JSON_PARSE_ERROR_MESSAGE`: 「リクエストボディの形式が不正です。」`HttpMessageNotReadableException` 発生時に使用。
- `ErrorMessage.DEAFALT_BAD_REQUEST_MESSAGE`: 「不正なリクエストです。」`IllegalArgumentException` などで明示メッセージが無い場合に適用。
- `ErrorMessage.MBR_CONFLICT_CODE`: 「会員コードは既に使用されています。」`DuplicateValueException` のレスポンスメッセージに利用。
- `ErrorMessage.IDE_DEFFERENT_REQUEST_MESSAGE`: 「同一Idempotency-Keyで異なる内容のリクエストが送信されました。」`IDEMP-0001` の文言。
- `ErrorMessage.IDE_SAME_KEY_RUNNING_MESSAGE`: 「同一Idempotency-Keyの処理が進行中です。しばらくしてから再実行してください。」`IDEMP-0002` の文言。
- `ErrorMessage.DEAFALT_INTERNAL_SERVER_ERROR_MESSAGE`: 「予期しないエラーが発生しました。時間を置いて再度お試しください。」`UnexpectedPersistenceException` や未知例外のレスポンスで使用。

## 6. 冪等性処理
- `MemberService` は `endpoint = normalizeEndpoint("/api/v1/members/create")` と `normalizedIdempotencyKey` を組にして `IdempotentRequest` を `PROPAGATION_REQUIRES_NEW` のトランザクションで確保する。
- 既存レコードが存在した場合は別トランザクションで読み出し、
  - `requestHash`（正規化後の `code|name|email|note` を SHA-256）差異 → `IdempotencyConflictException`（409, `IDEMP-0001`）
  - `memberId` 未設定 → 処理中とみなして `IdempotencyConflictException`（409, `IDEMP-0002`）
  - `memberId` 設定済み → 過去レスポンスを再生成して返却
- 新規登録成功時は `IdempotentRequest.memberId` と `responseBody` を更新して再実行時にキャッシュを返す。
- トランザクションがロールバックした場合は確保済みレコードを削除するクリーンアップを実施する。

## 7. データ一意性・整合性
- アプリ層で `MemberRepository.existsByCodeAndDeletedAtIsNull` により論理削除されていない会員コードの重複を事前検出する。
- データベース側では `V1__members_and_idempotency.sql` にて `members.code` に `deleted_at IS NULL` 条件付き部分一意インデックス `uq_members_code_active` を付与し、二重登録を防止する。
- 永続化時に `DataIntegrityViolationException` が `uq_members_code_active` 由来であれば `DuplicateValueException` に正規化し、その他は `UnexpectedPersistenceException`（500）として扱う。

## 8. ログ・トレース
- `CommonHeadersFilter`／`RequestIdFilter` は MDC に `traceId`／`idempotencyKey`／`rid` を格納し、処理終了後に除去する。
- 監査・アプリケーションログでこれら MDC 値を出力することで、トレースと冪等性キーの突合が可能となる。
