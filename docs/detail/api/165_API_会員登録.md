# 会員登録 API 設計書（v0.1 / ①段階）

## 基本情報
- **API名**：会員登録（Create Member）  
- **メソッド**：`POST`  
- **パス**：`/api/v1/members/create`  
- **主な機能**：会員（Members）を新規に登録する。ULID はサーバ側で生成し、会員コード（code）は未削除レコードに対して一意であることを保証する。

---

## 入力（リクエストボディ）とバリデーション
> 形式は JSON。未指定フィールドは省略（`null` は「値の明示的クリア」用途としては本APIでは非対応）。

| フィールド | 型 | 必須 | 説明 | ルール（APIバリデーション） | エラーコード例 |
|---|---|:---:|---|---|---|
| `code` | string | ✔ | 会員コード | 1〜50文字／前後空白除去／重複不可（未削除レコードに対して一意） | `VAL-0101` 必須、`VAL-0102` 長さ、`VAL-0103` 一意 |
| `name` | string | ✔ | 会員名 | 1〜200文字／前後空白除去 | `VAL-0201` 必須、`VAL-0202` 長さ |
| `email` | string |  | メールアドレス | 前後空白除去・小文字化／RFC に準拠したメール形式／最大320文字 | `VAL-0302` 長さ、`VAL-0303` 形式 |
| `note` | string |  | 備考 | 最大10000文字 | `VAL-0402` 長さ |

**一意性の判定条件**  
- `code` は **`deleted_at IS NULL`** のレコードに対してユニークであること。論理削除済みは競合対象外。

**補足**  
- ULID はサーバ生成につき、入力不可。  
- 将来の運用で `email` をログインに転用しないため、重複許容。

---

## 出力（レスポンスボディ）とバリデーション
> 成功時は登録の成否を返します。

| フィールド | 型 | 説明 | ルール（レスポンス検証の観点） |
|---|---:|---|---|
| `success` | boolean | APIの成否 | true/false（実質的にtrueのみ） |

**エラーレスポンス（例）**  
```json
{
  "timestamp": "2025-10-20T00:00:00Z",
  "traceId": "a1b2c3d4e5f6",
  "errorCode": "VAL-0105",
  "message": "会員コードは既に使用されています。",
  "field": "code",
  "details": ["members.code unique violation (active)"]
}
```

## 詳細設計（アプリケーションロジック）

### 1. 受信と正規化
1. JSON を受信し、DTO にマッピング。  
2. `code`, `name`, `email`, `note` に対して以下を実施：  
   - 前後空白の除去（trim）。  
   - `email` が指定される場合は**小文字化**。

### 2. 入力バリデーション
`入力（リクエストボディ）とバリデーション`に基づいてチェックを行う。
- 失敗時は **HTTP 400** として `{code, message, field}` 形式で返却。

### 3. 事前一意性チェック（業務制約）
- トランザクション開始。  
- `SELECT 1 FROM members WHERE code = :code AND deleted_at IS NULL FOR UPDATE` 
  - 一意制約違反の例外は 409 へ正規化。  既存があれば **409 Conflict**：`VAL-003`。

### 4. ULID 生成・監査情報設定
- `id = ULID()`（アプリ側で生成）  
- 監査：
  - `created_at = now(UTC)`
  - `updated_at = now(UTC)`
  - `created_by/updated_by` は実行ユーザーID（任意）

### 5. 登録（INSERT）
```sql
INSERT INTO members (
  id, code, name, email, note,
  created_at, created_by, updated_at, updated_by, deleted_at
) VALUES (
  :id, :code, :name, :emailOrNull, :noteOrNull,
  now(), :actor, now(), :actor, NULL
);
```
- DB側では以下の制約が最終防御：  
  - `ux_members__code_active`（部分一意）  
  - `NOT NULL` 制約（`code`,`name`,`created_at`,`updated_at`）  
  - `CHECK`（ULID 形式）

### 6. レスポンス整形
- `success`：true

### 7. レスポンス送信
1. DTO から JSON に変換し送信
---

## ロジック外設計

### 1. 例外処理（正規化）
- 400：バリデーション(`VAL-FFRR`)
- 409：一意制約（`VAL-0105`等）  
- 500：予期せぬ例外（`SYS-1001`等）  

### 2. 監査ログ
- 監査テーブル（または構造化ログ）に以下を記録：  
  - 操作種別：`MEMBER_CREATE`  
  - 主体（ユーザーID）、対象（member.id／code）、時刻、リクエストIP など

### 3. トランザクション
- ステップ 3〜7 を **1トランザクション** で実行（コミットは最後）。
